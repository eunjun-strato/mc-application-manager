Decision

왜 2376이 아니라 SSH 22인가?

2376도 올바르게 구성하면 안전합니다. 다만 이번 조건에서는 이미 멀티클라우드 SSH를 제공하는 Tumblebug을 활용하는 편이 운영 부담이 가장 작았습니다.

Boundaries

이번 수정으로 자동 해결되지 않는 것

SSH 22 전환의 경계를 알아야 운영에서 과도한 기대나 새로운 노출을 피할 수 있습니다.

1

보안그룹 규칙

AM은 기존 CSP 보안그룹의 2375 규칙을 자동 삭제하지 않습니다. listener와 별개로 불필요한 규칙은 운영자가 제거해야 합니다.

2

AM↔Tumblebug HTTP

같은 Compose 내부의 Basic Auth HTTP 구간은 이번 범위에 포함되지 않았습니다. Zero Trust 환경이라면 별도 TLS가 필요합니다.

3

대규모 모니터링

현재는 컨테이너별 SSH 조회입니다. 컨테이너가 많으면 VM별 일괄 조회와 동시성 제한을 후속 검토해야 합니다.

!
별도 보완 권장 원격 stderr 원문 로깅, 기존 Nexus 비밀번호 로그, MariaDB/MySQL 고정 기본값, Redis·Elasticsearch 보안 비활성 기본값은 SSH 전환과 별개의 보안 과제입니다.
FAQ

오해하기 쉬운 질문

정말 포트만 2375에서 22로 바꾼 것인가요?
아닙니다. 외부 API와 사용자 기능은 유지했지만, docker-java 기반 Remote API를 제거하고 명령 실행·파싱·컨테이너 ID 저장·모니터링까지 SSH 방식으로 다시 구성했습니다.
Kubernetes 배포도 SSH를 사용하도록 바뀌었나요?
아닙니다. Kubernetes는 기존과 동일하게 kubeconfig, Kubernetes API, Helm을 사용합니다. 이번 수정 대상은 VM Docker 경로입니다.
22번 포트는 공인 인터넷 전체에 열어도 되나요?
아닙니다. 가능하면 Tumblebug 관리 서버, VPN, 사내망 등 필요한 출발지만 접근하도록 보안그룹을 제한해야 합니다.
VM에 공인 IP가 없어도 Docker 배포할 수 있나요?
AM이 2375로 직접 접근할 필요는 없어졌습니다. 다만 Tumblebug이 해당 VM의 SSH 22에 도달할 수 있는 사설망·VPN·bastion 등의 네트워크 경로는 필요합니다.
왜 TLS가 있는 2376을 사용하지 않았나요?
2376은 보안상 올바른 선택이 될 수 있지만 VM별 인증서 수명주기를 운영해야 합니다. 이번 조건에서는 이미 있는 Tumblebug SSH 키 관리 체계를 활용하는 것이 더 단순했습니다.
Observability도 SSH로 바뀌나요?
별도 MC-Observability 플랫폼은 변경되지 않습니다. AM 자체가 Docker 컨테이너 상태와 통계를 확인하던 경로만 2375에서 Tumblebug SSH로 바뀌었습니다.
